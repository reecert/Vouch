# vouch — web

The product site, the connect flow, and the profile viewer. Next.js 15 (App Router),
React 19, TypeScript, Tailwind v4.

## Two halves that do not mix

| Route | What it is |
|---|---|
| `/`, `/how-it-works`, `/what-we-measure`, `/privacy`, `/connect`, `/dashboard` | The product. Session, GitHub sign-in, job queue. Grouped under `app/(site)/`, which is where the nav lives. |
| `/p/<id>` | One person's document. Outside the group, so it carries no product nav — a profile is read by someone who was sent a link, not by a visitor browsing a site. |

It used to be a static export. It is not any more, because profiles are generated by a
worker *after* the build and the set of them is not knowable at build time. What made the
export valuable is unchanged and does not depend on it: a profile is still one frozen JSON
file, written once, served as-is, and deleted outright when revoked.

## Running it

```sh
npm install
npm run dev                 # http://localhost:3000
```

Nothing but the marketing pages works without configuration. For the connect flow:

```sh
# web/.env.local  (gitignored)
GITHUB_CLIENT_ID=...
GITHUB_CLIENT_SECRET=...
NEXT_PUBLIC_SITE_URL=http://localhost:3000
```

Register the OAuth app at <https://github.com/settings/developers> with the callback
`<NEXT_PUBLIC_SITE_URL>/api/auth/callback`. `NEXT_PUBLIC_SITE_URL` is also what `canonical`
and `og:image` resolve against, so it must be the deployed origin in production —
it defaults to `http://localhost:3000`, which is right for `npm run dev` and wrong for
anything you actually share.

Queued jobs do nothing until the Python worker is running (from the repo root):

```sh
vouch worker            # polls; --once drains and exits
```

`npm run build && npm start` for production. The build needs no database and no GitHub
credentials — every page that touches either is rendered per request.

## State

One SQLite file, `../var/vouch.db`, written by both runtimes: this app via `node:sqlite`
(standard library) and the worker via Python's `sqlite3`. No broker, no ORM, no service that
has to be up for a page to render. `VOUCH_DB` overrides the path and must match on both
sides.

Generated profiles go to `../var/profiles/`, **not** `data/profiles/`. The second is tracked
and its bytes are pinned by a test; keeping them apart is what stops a real person's profile
arriving in a commit, and what puts the checked-in samples out of reach of the delete path.

## The share card

Every link unfurls to the same branded card — `public/og.png`, rendered from `og/card.html`.
It carries no profile content on purpose: unfurlers cache the image indefinitely, show it to
a whole channel rather than the one person who opens the link, and strip every denominator
and limitation the document is built from. A cached card cannot be withdrawn, so nothing
that would have to be withdrawable goes in it. `lib/share.ts` enforces the same rule for the
text beside it — it takes counts rather than a `Profile`, so the subject and the verdicts
are not in scope to leak.

Regenerate the PNG after editing the card (no build step reads `og/card.html`; the committed
image is what ships):

```sh
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new \
  --disable-gpu --hide-scrollbars --force-device-scale-factor=1 \
  --window-size=1200,630 --screenshot=public/og.png og/card.html
```

Any headless Chrome works; the card uses the system font stack, so a render on another OS
will differ slightly in metrics. `tests/test_web_share.py` checks the result is still
1200×630.

## What this app deliberately does not do

- **It computes nothing about a profile.** No score, no aggregate, no ranking — not even
  client-side. If the viewer could derive an overall number, the guarantee that the document
  carries none would be cosmetic.
- **It never asks GitHub for more than `read:user`.** It cannot read a private repository,
  cannot write anything, and the clone is anonymous — the token never reaches the process
  that runs git. Private-repo OAuth stays a phase-1 non-goal, structurally rather than by
  promise.
- **It does not accept a repository address.** `/api/jobs` takes a bare `owner/repo` and the
  worker builds the URL. A path, an ssh address, or a leading `--` is refused at the door;
  `tests/test_serve.py` asserts the pattern here and the one in `vouch/serve/db.py` are the
  same string.
- **It is not a directory.** The index lists the bundled snapshots under `next dev` only. A
  browsable list of everyone profiled is a candidate directory, an explicit phase-1
  non-goal, and `test_web_share.py::TestLandingPage` holds the guard in place.
- **It does not corroborate.** A profile generated here is git-only, because
  `~/.claude/projects` is on the subject's laptop. The affected dimensions report
  `not_collected` rather than leaving the gap unmarked.
- **Declining verdicts are styled neutrally.** "Insufficient evidence" is a normal, frequent
  outcome of an honest profile; rendering it in alarm colours would teach readers to see it
  as a mark against the candidate, which it is not.

## Sample snapshots

The two profiles in `data/profiles/` are generated from **synthetic fixture repos** with a
mock judge (`with-telemetry`, `git-only-solo`). They exist to exercise the viewer's range —
one with session telemetry, one git-only where planning discipline is `not_collected`.
Nothing in them describes a real person.

A snapshot's filename is its `profile_id`, and that id is a hash of the file's own contents,
so a hand-edited snapshot is a document whose id no longer describes it. Regenerate rather
than edit: `tests/test_web_share.py` recomputes every stored id and fails on the difference.
